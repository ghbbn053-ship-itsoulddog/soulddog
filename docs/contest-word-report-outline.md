项目名称建议：

`学途智伴：面向大学生的个人校园智能平台`

副标题可选：

`融合教务系统、学习平台、个人知识库与 MCP 能力的校园智能平台`

## 1. 项目摘要

### 本章写什么

- 用 200 到 300 字说明项目是什么
- 说明解决什么问题
- 说明核心方案和项目价值

### 参考文案

学途智伴是一款面向大学生的个人校园智能平台，核心目标不是构建一个泛化的聊天机器人，而是围绕学生在校内真实、高频、长期存在的学习与信息获取需求，建立一个连接教务系统、学习平台、个人知识库与智能服务能力的个人校园中枢。项目当前已具备教务系统登录、基础教务数据查询、工作区管理、知识库管理、聊天接口、学习平台二维码接入以及面向外部智能体的 MCP 能力输出基础。通过统一整合课表、成绩、培养方案、课程资料、历史提问与学习行为数据，平台能够逐步形成对学生课程路径和学习状态的持续理解，并通过 Web 端和 MCP 接口提供可复用、可扩展、可长期使用的校园智能服务。

## 2. 项目背景

### 本章写什么

- 说明为什么大学生需要这样的产品
- 说明现在校园里信息和学习工具为什么割裂

### 参考文案

在高校学习场景中，学生每天都会与多个系统发生交互，包括教务系统、在线学习平台、课程资料文档、个人笔记以及各种临时性的信息查询工具。然而，这些信息与服务长期处于分散状态：教务系统负责课程和成绩，学习平台承载课程内容，个人资料分散在本地文件和聊天记录中，AI 工具又往往缺少真实校园上下文，无法与学生个人课程情况和学习轨迹建立稳定关联。

这种割裂带来的直接结果是：学生虽然拥有大量数据和资料，却很难真正高效地使用它们。查询校园信息需要多次切换系统，学习资料难以沉淀为可持续利用的知识资产，通用 AI 虽然可以回答问题，却不理解学生当前修读的课程、培养方案要求以及个人薄弱点。由此可见，大学生真正需要的不是一个泛泛回答问题的 AI 页面，而是一个建立在真实校园场景和个人学习过程之上的长期智能平台。

## 3. 用户痛点分析

### 本章写什么

- 拆成几条具体问题
- 不要泛泛而谈

### 参考文案

第一，校园信息分散，查询成本高。学生在查看课表、成绩、培养方案、考试安排、选课信息等内容时，通常需要分别进入不同页面甚至不同系统，操作重复且效率较低。

第二，学习资料虽多，但缺少统一沉淀与调用机制。课程 PPT、讲义、笔记、习题和个人总结往往保存在多个位置，难以形成持续积累的个人课程知识库。

第三，现有通用 AI 工具缺乏校园语境。普通大模型虽然能够回答概念性问题，但并不了解学生当前课程安排、个人培养方案、学习平台内容和历史提问背景，因此回答往往停留在泛化层面。

第四，学生的学习过程缺少连续追踪。当前多数工具只能完成单次问答或单次查询，无法随着使用过程逐步理解学生真正不懂的内容、课程掌握情况以及后续需要复习的重点。

第五，校园智能能力难以复用。即使某些能力已经在平台内实现，如果不能以标准接口形式向外部智能体开放，就难以形成更广泛的应用生态。

## 4. 项目目标与产品定位

### 本章写什么

- 给出一句话定位
- 写清项目目标

### 参考文案

本项目定位为“面向大学生的个人校园智能平台”，也可进一步概括为“学生个人校园学习中枢”。其核心不是做一个附加型聊天入口，而是围绕学生个人课程、学习资料、学习行为和校园服务需求，构建长期可用、持续沉淀、可扩展复用的智能基础设施。

项目目标主要包括以下四点：一是打通教务系统、学习平台、个人知识库与智能服务之间的数据链路；二是提升学生获取校园信息与管理课程学习的效率；三是让 AI 从一次性回答问题升级为能够持续理解个人学习路径的长期助手；四是通过 MCP 等标准化方式，将平台能力输出给外部智能体，实现校园能力复用。

## 5. 项目整体方案

### 本章写什么

- 先总述
- 再引出四层结构

### 参考文案

为解决上述问题，学途智伴采用“校园数据层—学习平台连接层—个人知识库层—智能服务层”的四层结构设计。该方案既考虑了当前校园系统缺少统一 API、数据结构不一致、登录流程复杂等现实问题，也兼顾了知识沉淀、智能问答、能力开放和后续扩展等长期需求。

在整体思路上，平台先通过统一身份入口获取学生真实校园数据，再结合学习平台和知识库形成以课程为中心的个人学习上下文，最终通过 Web 界面和 MCP 工具形式向内外部提供标准化智能服务。这样的平台既能满足学生个人使用，也具备后续扩展为校园智能能力底座的潜力。

---

## 6. 四层架构设计

### 本章写什么

- 分四段写
- 每层都要写“做什么、解决什么问题”

### 参考文案

（1）校园数据层。该层主要负责教务系统相关数据的接入、解析、结构化存储与缓存，包括个人信息、课表、成绩、培养方案、学业进度、考试安排等内容。当前项目已具备教务系统登录链路和多类教务查询接口基础，并支持后端统一管理用户教务 session。该层的价值在于将高频校园信息从“分散页面查询”转化为“结构化智能调用”。

（2）学习平台连接层。该层主要负责接入在线学习平台，如超星、雨课堂等，通过二维码登录、课程列表获取、课程信息同步和学习状态记录等方式，形成学生在学习平台侧的课程概览与行为数据。当前项目已经具备超星与雨课堂二维码接入相关接口和服务雏形，可作为后续课程级学习画像构建的基础。

（3）个人知识库层。该层支持学生将课程相关文档、笔记、讲义、资料等沉淀为工作区知识库，并围绕课程主题进行管理、检索与后续智能问答。当前项目已经具备工作区管理、知识库文档写入、文档查看与分块管理等能力。该层的核心意义在于把零散资料转化为可长期积累的个人知识资产。

（4）智能服务层。该层通过前端聊天界面、后端 API、MCP 工具目录与远程 MCP 服务，把平台能力统一对外提供。当前项目已经具备聊天接口、MCP 工具访问接口、Agent Access Token 机制以及远程 MCP 的 streamable_http 和 SSE 入口。该层使平台不再只是一个单体应用，而是成为可被外部 Agent 复用的校园智能能力底座。

## 7. 当前已实现的核心功能

### 本章写什么

- 这一章只写已实现
- 不要混入未来规划

### 参考文案

目前项目已经完成并具备基础演示条件的能力主要包括以下几个方面。

第一，教务系统登录与身份同步能力。平台已具备验证码获取、登录验证、基础身份同步与会话管理能力，可作为后续个人教务数据服务的统一入口。

第二，教务数据查询能力。后端已提供个人信息、学籍卡片、成绩、课表、培养方案、学业进度、考试安排、选课信息、执行计划等多类查询接口，说明平台已经具备校园核心数据服务基础。

第三，工作区与知识库管理能力。平台已支持创建工作区、管理工作区、向工作区写入文本资料或文档，并进行知识文档概览和分块查看，为课程资料沉淀提供了基础容器。

第四，智能聊天与上下文扩展能力。平台已具备聊天接口，并围绕教务数据、工作区知识和学习记忆设计了上下文注入与辅助回答逻辑，为后续课程级智能问答打下基础。

第五，学习平台接入基础。当前已具备超星和雨课堂二维码登录相关接口与服务，为后续课程同步、学习进度分析和学习画像构建提供了基础条件。

第六，MCP 与 Agent 能力输出。平台已具备 MCP 工具目录、工具调用接口、Agent Access Token 管理以及远程 MCP 接入能力，支持外部智能体在不直接持有教务账号的前提下复用平台已授权能力。

## 8. 核心创新点

### 本章写什么

- 单独编号列出 4 点

### 参考文案

（1）场景创新：从通用聊天 AI 转向大学生个人校园中枢。项目不是泛化问答工具，而是围绕课表、成绩、培养方案、课程资料和学习行为构建的校园专属智能平台。

（2）数据融合创新：打通教务系统、学习平台、个人知识库与历史交互。项目将原本彼此分离的校园业务数据与个人学习资料统一到同一个用户语境之下，形成以学生为中心的长期数据链路。

（3）服务形态创新：从单体应用升级为可复用能力平台。平台不仅提供 Web 使用入口，还通过 MCP 能力向外部 Agent 输出课表查询、培养方案查询、学习信息概览等标准化服务。

（4）长期个性化创新：从一次性问答升级为持续学习支持。项目希望让 AI 不只回答单个问题，而是逐步理解学生的课程路径、知识薄弱点与学习偏好，形成长期可沉淀的个性化智能助手。

## 9. 技术实现方案

### 本章写什么

- 按前端、后端、数据、智能能力、安全隔离来写

### 参考文案

项目整体采用前后端分离的架构设计。前端以 Next.js 为基础，负责登录入口、工作区、知识库、MCP 页面、聊天页面和学习状态展示等交互界面；后端以 FastAPI 为核心，负责身份校验、教务数据抓取、学习平台接入、知识库服务、聊天上下文构建以及 MCP 服务输出。

在数据处理上，平台通过教务查询接口和学习平台接入服务获取学生个人数据，并进行结构化归一与缓存管理；通过工作区机制管理个人知识库文档，并为后续课程级检索与问答提供基础。

在智能能力上，平台已具备聊天接口、教务数据注入、工作区知识上下文接入和学习记忆扩展的技术基础，后续可进一步加强课程级 RAG、学习薄弱点识别和学习建议生成能力。

在平台开放上，项目已通过 Agent Access Token 和远程 MCP 服务实现平台能力输出，使 OpenClaw、Claude Desktop 等外部智能体能够在统一授权体系下复用平台服务。

在安全设计上，平台强调基于用户名的隔离校验、会话绑定、Agent Token 控制和远程调用鉴权，保证不同用户之间的数据不混用，避免外部 Agent 直接接触原始校园账号密码。
